1dsh 里现在跑着谁

dsh 的插件是一张平铺的名单。名单里有一格专门管"所有大模型"——它自己不会调模型， 只负责收别人的接入。谁想供模型，就插到这一格上。

llm 管所有大模型的那一格。自己不供模型，只提供"接入位"。 在跑
dsh-provider 我们的插件。插在上面那一格上，供模型。 在跑
llm-pi-ai 原来供 pi-ai 那 41 家模型的。被我们关掉了。 已关闭
llm-deepseek 原来单独供 DeepSeek 的。也被关掉了，DeepSeek 改走 dsh-provider。 已关闭
关掉上面两个、只留自己，是因为接入位不支持"覆盖"——同一个名字被人先占了，后面再插就直接报错。

所以供给模型的口子现在只有一个：dsh-provider。

2dsh-provider 里面装了什么

盒子里分三块：我们自己写的、从别处拷来的那份代码、我们自己下载的 pi-ai 库。

我们自己写的

放在 lib/
lib/index.js
插件入口。启动时把供模型的活转交出去，另外开 8 个网页接口。
lib/adapters/
查各家 provider 的余额/额度，9 家各一个文件。
lib/client.js
浏览器端：模型选择器、设置页的 Provider 标签。
lib/routes.js 等
路由发现、凭据体检、候选清单。
cordis.patch.yml
关掉上面那两格、插入自己、声明 DeepSeek 的地址。

不是我们写的

放在 vendor/llm-bridge/
lib/index.js（拷来的）
真正干活的：注册接入位、发请求、收流、翻译格式。跟模型说话的全在这儿。
node_modules/@earendil-works/pi-ai
一条软链，指向下面那份热更新的 pi-ai。它存在只为了让上面那份代码里的 import "…pi-ai" 落到我们自己的 pi-ai 上。
vendor/pi-ai/<版本>/
后台下载的 pi-ai（dsh 自带的是 0.84.4）。模型清单、各家协议实现都在这儿。
vendor/node_modules/（兜底依赖）
vendor/package.json 锁死一个验证过的 pi-ai 版本。 热更新不下到 / 下了但不合格时就用它——它和热更新目录互不覆盖。
用哪一份？启动时逐个"体检"挑出来的。
候选三档按优先级排：热更新下来的（新→旧）→ 兜底依赖 → dsh 自带。 体检就是照着那份代码的 import 需求生成一个探针模块试一遍，第一个通过的中选。
为什么不"先加载、失败了再退回"：Node 加载失败的 ESM 会留下半初始化记录，同一个文件没法重试。 所以判断只能在加载之前做。选中兜底那份时不挂软链——删掉它，Node 自然往上找到 node_modules。
为什么非要拷一份？
那份代码里写的是包名（"@earendil-works/pi-ai"），不是路径。包名由 Node 按"文件在哪儿"往上找。 放在原来的目录，找到的就是 dsh 自带的旧 pi-ai；拷到我们自己的目录，往上找就找到我们的软链、落到新版 pi-ai。
不拷贝的唯一办法是去改 dsh 全局安装里的 pi-ai —— 那是往宿主目录写东西，不允许。

3一次模型调用怎么走

从 agent 决定用哪个模型开始，到真正发出 HTTP 请求。

① agent 循环
决定这轮用哪个 provider / 模型
→
② 管大模型那一格
按 provider 名字挑出该由谁负责
→
③ dsh-provider 注册的接入
启动时注册进去的那个 adapter
→
④ 我们的 pi-ai
0.85.1，出模型清单和协议实现
→
⑤ 模型服务商
真正发 HTTP，收流
← 返回的流按原路回到 ①，逐块吐给界面
注意：这次调用里，dsh-provider 自己写的那部分代码一行都不跑。
lib/adapters/、lib/client.js、那 8 个接口全都不参与。 插件的作用只在启动那一刻——把 ③ 那个接入注册进 ②。之后每次调用走的是 ③④ 的代码。

密钥也是 ③ 自己去取，不经过我们的代码。我们写的取密钥逻辑只服务于余额查询。

5三句话记住

  • 位置是我们的，代码不是。供给模型的那一格现在属于 dsh-provider，但里面干活的代码是拷贝来的。
  • 我们自己的代码管界面和余额。跟模型说话这件事，我们没写一行。
  • 没有退路，但有兜底。原来两个供模型的都关了，只剩 dsh-provider 一个。它的代码加载不出来 就一个模型都用不了——所以插件启动时会先体检挑一份能用的 pi-ai，坏的版本根本不会被切过去。
