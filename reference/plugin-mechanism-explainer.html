dsh 插件机制图解

一个问题：如果插件机制非常底层，那和"起一堆进程"有什么区别？ 答案是 Cordis 内核给每个插件提供了四样进程没有的基础设施：服务板 · 依赖等待 · 可逆生命周期 · 拦截式事件总线，外加一个负责组装的 Loader。本页由浅入深逐层拆开。

01全景：两棵同构的插件树

先看格局。dsh 是两棵组织方式完全相同的插件树（host / 浏览器），各自挂在薄薄的启动壳之下，中间用三条类型化的"电话线"相连。插件机制负责：树内组合、树交付、跨树连线。

图 1 · 两棵树的组织方式一模一样：启动壳 → 根 Context → 一堆平等插件。跨树只有三条有名字的线。

02基础设施 ①：服务板 —— 按名字找能力，而不是 import 文件

进程间通信要序列化，插件间通信只是"从板上拿一个对象引用"。插件不互相 import；一个插件把自己的能力以一个稳定名字放到板上（ctx.tools、ctx.llm…），别的插件按名字来取。名字表是全局唯一的，官方维护 74 个服务的地图。

图 2 · 服务板：插件之间唯一的互相发现方式。这是"插件"和"进程"的第一道分野——进程靠端口/协议，插件靠名字/引用。

03基础设施 ②：依赖等待 —— 顺序不用你管，缺什么就等

清单里第几行不决定启动顺序。插件声明 inject = ['tools', 'llm'] 意思是"我需要这两样"。板上没有？它就处于 pending，不报错；谁把服务放上来，它那一刻自动激活。激活顺序是从依赖图推导出来的，这也是为什么插件列表可以随意叠层重排。

图 3 · inject 是"声明需求"而非"指定顺序"。系统替你解依赖、等依赖、并在依赖消失时收拾残局。

04基础设施 ③：可逆生命周期 —— 注册即留收据，卸载级联撤销

这是插件和进程的第二道分野。进程没有"半开"状态；插件的每一个注册动作（挂服务、注册工具、订阅事件）都通过 ctx.effect() 进行，系统记下一张收据。插件被卸载/热替换时，按相反顺序把收据全部兑现——注册的东西全部消失，不留残渣。所以热重载、按会话组装、按需拆装，都是安全的。

图 4 · 效果（effect）是可逆的。这使热替换、按会话临时组装、失败回退都成为框架级能力而不是应用自己操心的事。

05基础设施 ④：事件总线 —— 而且带"拦截"（这是和进程模型的本质不同）

普通事件是"广播"：发生了，大家各自反应。Cordis 的事件有五种派发模式，其中 waterfall（瀑布） 是 around-中间件：监听器拿到 (参数, next)，可以改参数再 next() 传下去、可以包一层计时、也可以直接短路替所有人做决定。工具的权限审批、请求改写、超时包装，全是这一条机制。拦截是一等公民，不是事后打补丁。

图 5 · 事件即扩展点。dsh 的"官方扩展点地图"本质就是一张事件/服务清单：每个功能都是某事件上的一串瀑布监听器。

06组装者：Loader —— 把"叠层补丁"变成一棵活的树

以上四样是插件运行时的生态；Loader 负责"谁上场"。它读插件清单（YAML 数组），把各层补丁叠成一个最终列表，逐个 import、逐个挂成 fiber，解 inject 依赖、处理 !!js 配置表达式、失败即响亮报错。补丁层序：官方基础包 → 界面包 → 你装的插件包 → 你的个人补丁 → 命令行 overlay，后写的赢。

图 6 · 组装是纯文本运算 + 动态挂载：任何人不用改别人的代码，就能往系统里插东西、改配置、关功能。

07所以，和"一堆进程"到底差在哪

图 7 · 插件系统卖的正是这四样"进程不给"的东西。Loader + 补丁层解决"谁来上场"，四样基础设施解决"上场之后怎么共处"。
