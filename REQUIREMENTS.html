dsh-provider · 系统需求与方案

给 dsh 提供 LLM 服务的插件：自动跟进 pi-ai 上游让新模型立即可用、为各 provider 查额度/余额、 接管模型选择器并显示余额，以及让配置错误可诊断。本文按「问题 → 功能方案 → 技术方案 → 缺口」四幕组织，供核对方案与需求。

第一幕

问题是什么

三个问题分别来自两份调研的结论（额度 API 调研 2026-09-11、插件架构调研），它们共同定义了这个插件的存在理由。

P1
模型目录滞后

新模型要等 dsh 发版

dsh 打包时固定了旧版 pi-ai（实测 0.84.4，上游已到 0.85.1，一次差 70 个模型）。 上游发了新模型，用户拿不到，只能等 dsh 下一次发版。

证据：README「原理：桥接层」；2026-09-12 实测
P2
额度不可见

「还剩多少」只能登控制台看

dsh 没有任何额度/余额设施（调研结论：从零建）；五家 provider 无一返回 rate-limit 响应头； 各家额度端点散在各处，格式不一。用户选模型时看不到哪个 provider 快没额度了。

证据：dsh-plugin-architecture.md §7；provider-quota-apis.md §5
P3
配置错误不可诊断

填错 key 只剩「查询失败」

浏览器端拿不到 key 值（credentials 单向流动），跨 provider 错配在界面上无迹可循。 实测案例：KIMI_CODING_API_KEY 被填成了 DEEPSEEK_API_KEY 的同值， 表现只是 kimi 一直查询失败。

证据：README「已知状态」2026-09-13；凭据体检一节

P1 的直观样子：发布节奏错配

第三幕

技术上怎么解决

一条主线：宿主半区代持密钥、代查额度、代管桥接；浏览器半区只做呈现与交互。 两半区之间只走同源 HTTP，这条边界同时决定了安全模型。

总架构：宿主半区 / 浏览器半区 / 同源 HTTP 边界

桥接机制放大：拷贝 + 软链，升级 = 换软链 + 重启

额度查询链路：一次 /plan/status 的完整路径

座位接管：single 座位的 priority 遮蔽

关键决策与非目标

决策 D1

host↔client 走自建 HTTP（Route A）

第三方插件拿不到 Typert 代码生成器，走不了 RPC 正规军；自建路由与 GUI 同源，浏览器裸 fetch 即可。代价：无鉴权层（见安全边界）。

决策 D2

client 端手写 classic script，无构建

浏览器包必须是固定 window.__ModuleLoader__.load 形状的 classic script；只内联不引依赖。开发时改完即生效。

决策 D3

数据面与官方完全同路

模型目录走 session/modelCatalog、切换走 session/selectModel、优先官方 modelDirectories 服务——官方行为不变，我们只做呈现层增强。

非目标（明确不做）理由（来源）
不依赖浏览器登录态 / token额度查询只吃 API key（Tier 1 原则，provider-quota-apis.md）
Qwen Token Plan 不做轮询无公开端点且 ToS 明示仅限官方工具交互使用
不基于 rate-limit 响应头推断额度五家均不返回相关头，实测否定
不用 chat completion 当探针烧 credit 且有 ToS 风险
不接入 Kimi 控制台 JWT 接口依赖网页登录态，违反 Tier 1；逆向记录备查
key 值不出宿主进程浏览器只拿结论与元信息
不改官方插件文件接管只经 cordis.patch 禁用行 + slot 优先级遮蔽
安全边界：dsh webserver 按设计无鉴权层，默认只绑 loopback，本插件的路由不做校验，前提即「仅本机可达」。 若宿主被配置为 0.0.0.0 暴露，/plan/status（余额、凭据名）与 POST /provider/update （触发公网下载 + npm install）将无防护——部署时必须意识到这一点。
第四幕

缺口与已知缺陷

基线之外的两类遗留：正式需求但未实现（用户确认保留在需求内），以及 review 发现的缺陷。 这一幕是「核对需求」时最需要对账的部分。

需求缺口（正式需求，当前未实现）

编号需求说明与依赖状态
G1侧边栏 sidebar.footer.action 入口形态待定：额度徽标或跳转 Provider 设置页❌ 缺口
G2shell.overlay 全局额度徽标可行性已被 demo 插件验证（图 5）；§G3 的实时用量数据是它的主要数据源❌ 缺口
G3用量统计与失败归因（原始调研 §7.3，本期需求）：监听 llm/stream 累计 token 用量；session/event 持久用量；llm/retry 的 QUOTA/RATE_LIMIT 归因；经 sessionProjections 推送浏览器与现有额度轮询互补不替代：轮询回答「账户还剩多少」（小时级），G3 回答「这次会话用了多少、刚才为什么失败」（秒级/事件级）❌ 缺口

已知缺陷（2026-09-13 review 发现，待修）

🐞 /provider/status 状态文件断链。updater.js 把 needsRestart / latestVersion 写进 vendor/status.json，而路由读的是 vendor/updater-state.json（只有 lastCheck/at）， 且全库无任何读者读 status.json。后果：设置页「已下载待重启」提示、上游版本显示、needsRestart 横幅永不出现； catalogPatches 字段宿主端从未产出，是死 UI。 修法：readStateFile() 合并两个状态文件。详见 REQUIREMENTS.md §8。

并发无锁

后台自动检查与 POST /provider/update 可并发对同一版本目录 rmSync + 重装；/plan/status 无请求合并，缓存落定前的并发请求会重复打上游。影响小。

rpcId 同毫秒碰撞

client 的 rpcId 用 Date.now() 生成，同毫秒两请求会撞 id；HTTP 成对收发，仅 cosmetic。

死代码分支

resolveKey 里 typeof resolved === 'string' 分支永远不会命中（credentials.resolve 只返回对象）。无害。

验收标准速查

  • 离线测试三条全绿：node test/routes.mjs · node test/credential-check.mjs · node test/client-smoke.mjs

  • 桥接：上游新版自动就位 → needsRestart 提示出现 → 重启后新模型可见 → 回滚后目录恢复
